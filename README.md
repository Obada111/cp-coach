# CP Coach

A personalized Codeforces training dashboard with rule-based weakness analysis, exactly three daily recommendations, contest tracking, spaced review, solve-session reflections, and progressive tutorials. Daily boundaries use `Asia/Hebron`.

## What it does

- Uses only public Codeforces endpoints (`user.info`, `user.rating`, `user.status`, `problemset.problems`).
- Analyzes submissions and feedback with an evidence threshold; topics with fewer than three attempts are shown as **Unexplored**, not weak.
- Produces exactly three daily problems:
  - **Weakness Drill**: a weak topic near the current rating.
  - **Reinforcement**: another weak or hint/editorial-heavy topic.
  - **Challenge**: a stretch problem above the current rating.
- Excludes solved problems and recent assignments. Existing daily sets are idempotent and are not regenerated by refreshes.
- Tracks contests, post-mortems, self-reviews, upsolving, spaced review, weekly goals, and solve sessions.
- Automatically schedules review after struggles, reports evidence from two weekly windows, and shows recent per-topic learning history.
- Provides a searchable, browser-private concept journal and timed virtual runs of imported past Codeforces contests.
- Keeps verified Codeforces accepts separate from self-reported outcomes.
- Supports opt-in Web Push reminders for upcoming Codeforces contests and unfinished daily practice through a Cloudflare-scheduled background worker.
- Saves an offline dashboard snapshot in the browser and supports versioned JSON export/import of public-mode learning state.
- Installs as a lightweight PWA; only the app shell and static, same-origin assets are cached, never API responses.

## Architecture

| Part | Technology | Hosting |
| --- | --- | --- |
| Frontend | React 18, Vite, TypeScript, Tailwind, Recharts | Vercel Hobby |
| Backend | Node.js 24, Express, TypeScript, native `node:sqlite` | Render Free |
| Learning data | Versioned browser-local snapshot plus an ephemeral server copy | Visitor's browser + `/tmp` on Render |
| Notification data and scheduler | Cloudflare Workers Cron Triggers and D1 | Cloudflare Workers Free |

The public backend is intentionally tokenless. The browser sends a random `X-Coach-Client-Id` and the selected `X-Coach-Handle`; the server derives an isolated profile ID from them. A handle is not a password, so the client ID is the browser's access key. Clearing site data loses access to that browser's server-side copy.

The legacy profile/database API is mounted at `/api/admin` only in public mode and is disabled unless `COACH_ADMIN_TOKEN` is configured. The frontend never receives a server token.

## Local development

Prerequisites: Node.js 24+ and npm 10+.

```bash
npm install --prefix backend
npm install --prefix frontend
```

Start the backend:

```bash
npm run dev:backend
```

Start the frontend in another terminal:

```bash
npm run dev:frontend
```

Open `http://127.0.0.1:5173`. The Vite dev proxy sends `/api` to `http://127.0.0.1:3001`.

Local mode uses `backend/data/cp_coach.db` by default and keeps the existing `Obadajo` profile behavior. Set environment values in `backend/.env` (or export them) if needed:

```env
PORT=3001
HOST=127.0.0.1
DB_DIR=./data
PUBLIC_MODE=false
TIMEZONE=Asia/Hebron
```

## Public deployment

### 1. Backend on Render Free

Use the included `render.yaml` Blueprint. It:

- builds only the backend,
- runs with `PUBLIC_MODE=true`,
- sets `DB_DIR=/tmp/cp_coach` because Render Free storage is ephemeral,
- uses `/api/public/health` as the health check,
- does not create a paid disk,
- does not set a frontend-visible token.

After Render creates the service, note its HTTPS URL. Set `CORS_ORIGINS` to the exact Vercel production origin once the frontend exists. `ALLOW_VERCEL_PREVIEWS=true` optionally allows `*.vercel.app` preview origins.

If `CORS_ORIGINS` is unset, the public API accepts browser requests from any origin. That is functional, but setting the exact frontend origin is recommended.

Configure these server-only Render variables after creating the Cloudflare Worker:

- `CLOUDFLARE_NOTIFICATIONS_URL`: the Worker HTTPS origin.
- `CLOUDFLARE_NOTIFICATIONS_API_SECRET`: shared backend-to-Worker bearer secret.
- `VAPID_PUBLIC_KEY`: the public half of the existing stable VAPID key pair.

### 2. Frontend on Vercel Hobby

Import the same repository into Vercel. The included `vercel.json` builds `frontend/` and serves the Vite SPA.

Set these Vercel project environment variables:

```env
VITE_PUBLIC_MODE=true
VITE_API_BASE_URL=https://your-render-service.onrender.com
```

Do not add `COACH_API_TOKEN`, `COACH_ADMIN_TOKEN`, or any other server secret to Vercel. The frontend bundle must not contain server credentials.

### 3. Free-tier limitations

- Render Free may sleep after inactivity; the first request can take longer.
- Render Free has no persistent disk. The SQLite file is temporary.
- The sleeping Render API is used only to synchronize notification settings, subscriptions, and daily snapshots. Cloudflare owns notification persistence and scheduling, so push delivery does not require the Render process or browser to remain online.
- Each browser stores a versioned snapshot of its own assignments, feedback, notes, reviews, sessions, contests, and goals. The snapshot is restored after a backend restart.
- Use **Settings → Learning Data Backup** to export all saved handles or import a versioned JSON backup in merge or replace mode. Imports are validated and confirmed before use.
- Backups are limited to 10 MB; oversized exports fail explicitly instead of silently omitting records. Restores remap browser-owned IDs while preserving shared Codeforces problem identities.
- Weekly reports use seven Asia/Hebron calendar dates and timezone-aware UTC boundaries, including daylight-saving transitions.
- PWA offline mode can show the last browser-saved dashboard. Codeforces and API data are not presented as current while disconnected.
- Browser-local data is not synchronized between devices. Two browsers are separate tenants even for the same handle.
- The service can still lose data if a browser's site data is cleared and the backend is restarted.
- No keep-alive traffic is generated. Auto-refresh runs only while the page is visible.

## Push notifications and reminders

The existing PWA service worker receives Web Push and displays notifications using `showNotification()`. A Cloudflare Worker Cron Trigger runs independently of Render and the browser; it stores only notification data in D1. No browser polling, Render keep-alives, paid scheduler, or in-process public Render worker is used. Users explicitly enable notifications in **Settings** on each browser/device.

### Cloudflare setup and deployment order

No Cloudflare resource has been created or deployed by this repository. Do not run the remote commands below until you are ready to create the account resources.

1. Sign in to Cloudflare and enable the **Workers & Pages** Free plan. Create no paid resources. Install Wrangler or use the pinned local CLI:

   ```powershell
   cd cloudflare/notifications-worker
   npm ci
   npx wrangler login
   ```

2. Create the notification-only D1 database and let Wrangler update the local config:

   ```powershell
   npx wrangler d1 create cp-coach-notifications --update-config
   ```

   Confirm `database_id` in `wrangler.jsonc` was filled with the returned ID. Do not change the binding name `DB`. Apply the additive schema locally first with `npm run db:local`. When reviewed and ready, apply it remotely:

   ```powershell
   npx wrangler d1 migrations apply cp-coach-notifications --remote
   ```

   This migration creates only notification-specific tables. It does not move, alter, or delete application SQLite data or browser backups.

3. Keep the existing VAPID key pair; do not rotate it. Configure secrets for the Worker from `cloudflare/notifications-worker`:

   ```powershell
   npx wrangler secret put API_SECRET
   npx wrangler secret put VAPID_PUBLIC_KEY
   npx wrangler secret put VAPID_PRIVATE_KEY
   ```

   Generate one long random `API_SECRET` locally (for example `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`), save it securely, enter it when Wrangler prompts, and copy that same value into Render. The private VAPID key must exist only as a Cloudflare Worker secret (and in your secure private backup), never in Vercel or the public bundle. The public VAPID key also goes in Render as `VAPID_PUBLIC_KEY` so the existing browser subscription flow continues using the unchanged pair. Set `VAPID_SUBJECT` in `wrangler.jsonc` to the contact URI used by the existing pair; reminder calculations always use Asia/Hebron.

4. Deploy the Worker:

   ```powershell
   npm run deploy
   ```

   The config installs the single native Cron Trigger `*/5 * * * *`. It invokes the `scheduled()` handler without HTTP authentication; Cloudflare dispatches that event. Backend API operations use the separate `API_SECRET` bearer check. Confirm the trigger is shown in the Cloudflare Worker settings and the public `/health` endpoint responds.

5. In Render's server-side environment, set:

   - `CLOUDFLARE_NOTIFICATIONS_URL=https://<worker>.<account-subdomain>.workers.dev`
   - `CLOUDFLARE_NOTIFICATIONS_API_SECRET` to the same value as Worker `API_SECRET`.
   - `VAPID_PUBLIC_KEY` to the public key from the existing VAPID pair.

   `render.yaml` declares these variables as unsynchronized secrets. Never put the API secret or VAPID private key in Vercel.

6. Deploy the existing Render API and Vercel frontend through their normal dashboards. Render synchronizes settings, subscriptions, profile handle, and current daily recommendations to the Worker. The browser does not call Cloudflare directly. After deployment, re-open CP Coach on HTTPS and verify `/api/public/notifications/config` reports available.

### Notification behavior and identity

- Contest reminders are based on Codeforces' official contest list, cached for five minutes, and selected in the 30-minute pre-start window. Canceled/removed upcoming contests are marked canceled on refresh. Each profile/device/contest has a unique delivery key.
- Daily reminders default to **20:00 Asia/Hebron**. They require a same-day, fresh D1 snapshot containing at least one recommendation. Immediately before a push, the worker fetches Codeforces submissions and only `OK` accepted submissions count; opening a problem and self-reported completion do not. Missing, invalid, empty, stale, or unverifiable snapshots are skipped.
- Daily snapshots are synchronized from server-side recommendation/completion state after successful relevant API reads and updates. If Render is asleep or the user has not opened CP Coach after generating new browser-backed recommendations, Cloudflare cannot read localStorage. It skips an unavailable/stale snapshot instead of guessing.
- A browser-local profile can register multiple device subscriptions. Separate browser profiles are not automatically linked even if they use the same Codeforces handle. Clearing that browser's site data may prevent later preference/subscription management. Existing browser backups remain unchanged.
- Delivery is idempotent in D1, failed deliveries may retry, 404/410 push endpoints are removed, and claims older than 15 minutes are recoverable after a Worker crash. Worker run and heartbeat data are available through `/health` and `notification_worker_runs`.
- Cleanup retains worker execution rows for 45 days, delivery rows for 180 days, and contest rows for 90 days. The Worker processes at most one push per five-minute run to constrain Free-plan CPU. This is up to **288 pushes/day total**; larger profile/device populations may be delayed and this is not a high-throughput notification service.

### Free-tier estimates, limits, and backups

- One Cron Trigger every five minutes uses **288 scheduled invocations/day**, or **8,640 per 30-day month**, plus backend HTTP API calls. The Workers Free allowance is 100,000 requests/day and has a 10 ms CPU limit per Cron invocation; only five Cron Triggers are allowed per account. Network wait does not count as CPU, but cryptography, JSON handling, and D1 query/result processing do. Current limits: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).
- D1 Free currently allows 10 databases/account, 500 MB/database, 5 GB total/account, 50 D1 queries per Worker invocation, and seven days of Time Travel. The worker uses a small number of indexed queries; account usage must still be monitored. Current limits: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/).
- Tests run under local Workerd and verify Web Push VAPID signing/encryption and delivery flow. Their `performance.now()` timings are wall-clock measurements, **not Cloudflare billed CPU**. Actual CPU usage is visible in Cloudflare Worker invocation logs/metrics after deployment; no production CPU benchmark or external push delivery can be reported before a user-authorized deployment with real D1 and device subscriptions. If Cron runs exceed 10 ms, do not treat Free as reliable until optimized or the architecture/plan is reconsidered. No paid plan is activated automatically.
- Cloudflare Free has no uptime SLA. Cron/API/provider outages or daily request limits can delay delivery; the Render API may sleep, while the Worker can continue from D1 snapshots.
- D1 Time Travel is automatic but Free retains only seven days. It is not a substitute for an independent backup. Export manually and store the SQL file securely outside the repository; it contains private push subscription material:

   ```powershell
   npx wrangler d1 export cp-coach-notifications --remote --output "$HOME\cp-coach-notifications-backup.sql"
   ```

   The repository does not run remote exports, restores, migrations, or deployments. Keep the existing browser data backups as well.

   To inspect recent executions directly:

   ```powershell
   npx wrangler d1 execute cp-coach-notifications --remote --command "SELECT started_at, completed_at, status, profiles_checked, pushes_attempted, notifications_sent, duration_ms, error_code FROM notification_worker_runs ORDER BY started_at DESC LIMIT 20"
   ```

### Android Chrome smoke test

1. After manually applying the remote D1 migration and deploying the Worker, verify recent successful rows from `notification_worker_runs` and check `https://<worker-host>/health`.
2. On Android Chrome, open the HTTPS app or install the PWA, then choose **Settings → Notifications → Enable Notifications** and grant permission. Permission is requested only after that click.
3. Enable contest/daily reminders. For a daily test, select a time a few minutes ahead and confirm today's recommendation snapshot is synchronized and unfinished. Contest delivery requires a real upcoming Codeforces contest within the 30-minute window.
4. Close CP Coach and lock the phone. Verify tapping a daily notification opens Daily Recommendations and a contest notification opens its contest. Complete all recommendations before the reminder to verify it is skipped.
5. Restore the normal reminder time and test disabling reminders/removing the device subscription.

## Browser-local persistence and refresh

- A visible tab refreshes approximately every 120 seconds and refreshes when it becomes visible again.
- Hidden tabs do not poll.
- The header shows the last successful update time.
- A failed refresh keeps the last valid dashboard and shows a notice.
- The service worker caches only the static app shell and Vite assets. `/api/` and `/health` responses are never cached.
- A backend restart is detected through the public health endpoint's instance ID; the browser re-uploads its snapshot before loading the dashboard.
- Successful mutations trigger a debounced context capture. The server copy is a convenience cache, not a permanent account store.
- The daily set is persisted server-side and restored from the browser snapshot, so a refresh does not regenerate the three recommendations or erase feedback.

## API boundary

Public endpoints are under `/api/public`:

- `GET /health`, `GET /profiles`, `POST /profiles`
- `POST /profiles/:id/select`, `DELETE /profiles/:id`
- `GET /handle/validate`
- `GET /context`, `POST /context`
- The dashboard, daily, history, journal, contests, tutorials, reviews, sessions, weekly goals, training plan, and skill-track routes, all scoped to the requesting browser profile.
- `GET/PUT /notifications/settings`, `POST/DELETE /notifications/subscriptions`, and `GET /notifications/config`, scoped to the requesting browser profile.

The public API applies:

- per-IP read/write limits,
- tighter limits for Codeforces-backed sync, contest import, and handle validation,
- no-store responses,
- input and handle validation,
- ownership checks for daily problems, review items, and solve sessions,
- admin routes closed by default.

## Privacy

- No Codeforces password or API key is requested.
- Private notes and feedback are scoped to the browser's random client ID.
- Never commit `*.db`, WAL files, backups, logs, or real environment files.
- The public frontend contains no server token.

## Troubleshooting

- **Codeforces rate limiting (HTTP 429):** cached data is served; retries back off automatically.
- **First request after inactivity is slow:** Render Free is waking up. The page shows loading/error states rather than discarding the last valid data.
- **Empty recommendations on a fresh backend:** wait for the automatic Codeforces sync, or use Refresh. The problemset cache rebuilds from the public API.
- **Port conflict:** change `PORT` or run Vite with `npm run dev -- --port 5174`.
